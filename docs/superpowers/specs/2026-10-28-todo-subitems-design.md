# 待办子项（checklist）+ 可编辑详情 + 纳入时间段总结 · 设计文档

日期：2026-10-28
状态：用户已定产品要求（四条验收标准）并委托直接实施 + 完工汇报；本文档记录方案与
实现者的微观决策（§6「我的调用」），随实现一并提交。

## 一、产品要求（用户原定，验收以此为准）

1. **不搞按 agent 的编辑权限**。可读性优先：标题一行可扫；agent 写 note 要短
   （更严的硬上限 + UI 默认折叠长文）。
2. **每条待办有子待办（checklist）+ 可编辑详情**。
3. **全部子待办完成后，父待办自动进「已完成」**（status → done + completed_at）。
4. **待办与已完成待办进入时间段工作总结**（按时间窗纳入新建/完成的待办；
   后端 `todosInWindow` 雏形接进生成与展示）。

本设计**取代** 2026-10-27 工作台设计文档中「不做子任务」的非目标（当时用户确认过
用不上，现在明确要 checklist；负责人/截止日仍不做）。

## 二、数据模型（lib/todos.mjs）

父待办新增两个可选字段（旧数据无这两个字段，读侧按缺省处理，**无迁移**）：

```
todo.items: [ { id, title, done, done_at } ]   // 子项，数组序即展示序
todo.note : string                             // 既有字段，语义升级为「可编辑详情」
```

- 子项：`id` = randHex(4)（父内唯一）；`title` ≤ 200 码位、必填；`done` 布尔；
  `done_at` 完成时刻（取消完成置 null）——供后续按子项归因时间。
- 每条待办子项数 ≤ 50（防滥用）。
- `note` 上限分级：**source ≠ 'user'（agent 来源）≤ 300 码位**（可读性硬约束，
  400 拒绝）；用户网页路径维持 2000。标题两来源同限 500（短标题靠写作约定 + UI 钳制，
  不另设 agent 数值——「一行可扫」由 UI 保证）。

## 三、自动完成规则（写清，smoke 逐条锁定）

任何**子项变更**（增/删/改，或 PATCH 父待办携带 items）后重derive 父状态：

| 变更后 items 状态 | 父状态派生 |
|---|---|
| 非空 且 全部 done | status=done；completed_at 原为空才盖（不重盖） |
| 存在未完成子项 且 父当前 done | status=in_progress，completed_at 清空 |
| 存在未完成子项 且 父非 done | 不动 |
| 空数组 / 无 items 字段 | 不动（父状态纯手动） |

- 取消完成回退目标是 **in_progress**（不是 pending）：取消意味着工作重新开始。
- **直接 PATCH 父 status 永远生效**（显式意图优先，允许「子项没勾完就手动完成」）；
  但之后的下一次子项变更会按上表重derive（显式状态只保到下一次子项操作）。
- 同一次 PATCH 同时给 status 与 items：先应用字段、后 derive——items 派生优先。
- 删到 items 为空：不再派生，父状态保持删除前值。
- 重新全部完成后 completed_at 重盖新时刻（上一轮已清空）。

## 四、API（/v1/todos，与工作台同源、Bearer 鉴权不变）

```
POST   /v1/todos                     # 既有；body 可选 items:[{title,done?}]（建带清单的待办）
PATCH|PUT /v1/todos/:id              # 既有；可选 items 整组替换（id 留则保留、缺则新派）
POST   /v1/todos/:id/items           # 加子项 {title, done?} → 201 {ok, todo}
PATCH|PUT /v1/todos/:id/items/:itemId # 改子项 {title?, done?} → 200 {ok, todo}
DELETE /v1/todos/:id/items/:itemId   # 删子项 → 204
```

- 子项端点响应**整只父待办**（含派生后的 status/completed_at），前端刷新即所见。
- 校验矩阵：子项标题必填 ≤200；items ≤50；未知 :id/:itemId → 404；
  agent note >300 → 400（文案点明分级上限）。
- 未知子资源（/v1/todos/:id/别的）→ 404。

方案取舍：**嵌套细粒度端点 + 父 PATCH 整组替换并存**——单操作（勾一个子项）一次
往返、并发不互相覆盖；整组替换给 UI 批量编辑与 agent 一次建单留便捷路径。仅整组
替换（无细粒度）会在「agent 勾子项」与「网页编辑」并发时丢更新，仅细粒度则建单
要 N 次往返，两者都要。

## 五、报告纳入（素材 → prompt → 展示）

- **素材**：`collectMaterials` 已并 `todosInWindow`；新增把两列表计数进报告
  `materials.todos = {created, completed}`（展示用）。
- **prompt**（lib/report-prompts.mjs）：
  - 「完成（N）」/「新增（N）」行保留；行带子项进度 `标题（k/j）`（k=已完成数），
    仅当尚有未完成子项时缀（手动完成的待办可能子项没勾完，此时完成行同样缀、如实呈现）；
  - 单标题截 40 码位（LIMITS.todoTitleChars）、每列表最多 30 条（todosPerList），
    超出加「等 N 条」——短列表，不灌长文；
  - note/详情**不进** prompt（可读性红线）。
- **空素材快径收窄**：原「四源会话为空且 0 字符 → 不调模型直接『无记录』」的快径，
  增加「且窗口内无待办变动」条件——只有待办进展也值得出报告（会话源失败照旧进
  `数据源状态` 附注，不把「源挂了」伪装成「无记录」）。
- **展示**：工作台成稿元数据行追加 `待办 新增 n / 完成 m`（有数才显）。

## 六、我的调用（用户未定、实现者拍板，汇报时点名）

1. 取消完成 → 父回 **in_progress**（用户给的选项二选一，理由见 §三）。
2. agent note 硬上限 **300 码位**（用户说「更严」，2000→300 一刀切到与素材
   userMsgChars 500 同量级以下；过长 400 拒绝而非静默截断——agent 能改文案重试）。
   上限按 **source 申报值**执行：共享 Bearer token 无法强校验调用方，agent 谎报
   `source:"user"` 可绕过——这是自觉约定 + 硬限兜底，不是权限边界（README 同口径）。
3. 子项标题上限 **200**、条数上限 **50**、子项 id randHex(4)。
4. 详情复用既有 `note` 字段（不新增 `details` 键，旧数据/旧调用方零迁移）。
5. UI 折叠形态：**收起行只显父标题（CSS 2 行钳制）+「子项 k/j」徽标**，note 在
   收起行完全不显（比行内截断更符合「默认折叠长文」）；展开区才见清单与详情全文。
6. 标题不设 agent 专属数值上限——「一行可扫」由 UI 钳制 + 文档写作约定保证。
7. 空 items（`[]`）= 无清单，不参与派生（避免「建单时传空数组把手动状态冲掉」）。

## 七、非目标

- 不做子项嵌套子项（一层 checklist）。
- 不做按 agent 的字段级编辑权限（用户明确不做；靠 note 短上限 + UI 折叠保证可读）。
- 不做子项单独的时间窗报告归因（done_at 落库备用，本次不消费）。
