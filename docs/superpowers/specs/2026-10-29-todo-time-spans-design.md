# 待办时段（time spans）+ 汇报正文按待办组织 · 设计文档

日期：2026-10-29
状态：用户已确认方案并授权直接实施。

## 一、要解决的问题

1. **汇报正文太繁杂**。现存真报告 896 字、4 个项目节，每节「一句总述 + 3 条长 bullet」。
   繁杂的原因是 prompt 直接要出来的篇幅（每节 2-3 条要点、成稿 600-900 字），换模型内核
   治不了。
2. **待办与汇报是两条平行线**。待办只出现在文末数据附注里，正文完全不提；没有出现在
   待办里的零散工作无法「简单带过」。

## 二、核心机制：时间重叠归属

会话素材（四个源）都带 `startTime` / `endTime`（消息级也有时间戳）。给待办加上**时段**后，
「这段会话属于哪条待办」可以纯按时间重叠算出来——确定性、可测、不依赖模型猜，也不依赖
`todo.project` 字段（用户的 project 填的是「黄区」这类，与会话的目录名对不上）。

- 每条待办有 0..N 个时段 `spans`。
- 一条会话与某待办任一时段**有交集** → 归入该待办。
- 未被任何时段覆盖的会话 → 汇报末尾「## 其他」一节，一行一条简单带过（用户明确要的效果）。

## 三、数据模型（lib/todos.mjs）

```js
todo.spans: [ { id, start, end } ]   // 数组序即展示序；end === null 表示仍在进行
todo.due_at: number | null           // 预计结束（用户说的「预计结束时间」），可选
```

- `start` / `end` 均为 epoch 毫秒；`end` 可为 `null`（进行中）。
- 同一待办的时段**不强制不重叠**（用户会来回切，硬校验只会碍事）；归属按「与任一时段有交集」
  判定，重叠不产生重复归属（一条会话只归第一条命中的待办）。
- 时段数上限 200/条（防滥用），`start` ≤ `end` 校验（`end` 非 null 时）。
- 旧数据无 `spans` 字段，读侧按空数组处理，**无迁移**。

### 全局单运行段

`end === null` 的时段**全局最多一条**。点某条待办的「▸ 开始」时：
1. 关掉当前任何运行中的时段（把它的 `end` 置为此刻）；
2. 为这条待办开一个新时段 `{start: now, end: null}`。

这样「A 干一半切 B 再回来 A」自然得到 A 的两段 + B 的一段，不需要用户打时间戳。

## 四、录入方式（两条都做）

用户没在「点按钮 vs 事后补填」之间选，两者场景不同，都实现：

- **实时**：行内「▸ 开始」/「✓ 完成」按钮顺带记录。`cycle` 到 `in_progress` 开段，
  到 `done` 关段。
- **补录**：展开区里的时段表，每段一行可改开始/结束（`datetime-local`），可删，可「＋ 加一段」。

## 五、页面改动（index.html）

1. **展开箭头恒显示**。现状是 `const expandable = items.length > 0 || Boolean(t.note)` ——
   干净的待办永远没有箭头，永远展不开，也就永远加不进第一条子项/详情。这是功能死角
   （数据层和展开区渲染都在，只是没人能进去）。改为恒显示。
2. 展开区新增「时段」块：列表 + 每行 `datetime-local` × 2 + 删除 + 「＋ 加一段」+ 预计结束。
3. 收起行 meta 行显示时段摘要：`3 段 · 2h15m`（或进行中时 `进行中`）。

## 六、汇报改造（lib/report/collect.mjs + report-prompts.mjs）

素材收集保持现状（四源并发、压缩、脱敏），新增**归属**一步：

- 每条会话按 `[startTime, endTime]` 与各待办的时段求交集，归入**第一条命中的**待办。
- 输出结构从「按项目分组」改为「按待办分组 + 未归属」：
  ```js
  materials.todoGroups = [
    { todo, sessions: [...], summaryText }   // 有素材的待办
  ]
  materials.unassigned = { sessions, summaryText }  // 没归到任何时段的会话
  ```
- 仍保留按项目归并的能力——**待办内部再按项目分**（一条待办可能跨多个项目目录）。

Prompt 改造（`report-prompts.mjs`）：

- 一级总结：按「待办 × 项目」出小结（一条待办下一个或多个项目片段）。
- 二级成稿：正文按待办分节（`## 待办标题`），每节写「做到哪了、产出什么」，段落短；
  末尾 `## 其他` 汇总未归属工作，**一行一条**。
- 篇幅收紧：有素材的待办每条 80-150 字，不再是每节 3 条长 bullet。

## 七、非目标

- 不做待办与外部系统（提醒事项 / 日历）的同步。`due_at` 只是字段，不参与联动。
- 不做「无时段待办也进正文」。没有时段就无法定位到窗口内，强行纳入只会让正文重新变长。
- 不改 `todosInWindow` 的三类计数口径（created/updated/completed 互斥规则不变）。

## 八、我的调用（实现者决策）

- **归属按「第一条命中」而非「最佳重叠」**：时段本就不该重叠太多，选最佳重叠会让结果对
  微小的时段调整敏感、难解释。第一条命中就是「先开始的那条」，符合直觉。
- **`due_at` 加上**：用户明确列了「预计结束时间」。虽然它不参与汇报，但成本极低，
  且是将来接提醒事项的锚点。
- **时段行用 `datetime-local`**：与报告区间选择器同一控件语言，无新依赖。
- **不校验时段是否落在报告窗口内**：用户可能补录窗口外的时段，交给归属计算自然过滤。

## 九、实施后的修订（同日晚）：时段方案撤掉，归属改由模型判断

上面 §三–§六 是**第一版实现**，已按实际使用证据推翻，代码里不存在了。留档说明为什么。

### 推翻的依据

方案上线当天统计运行时 `todos.json`：**6 条待办，0 条带时段**。用户当天在 50 分钟内
一次性录入全部 6 条，之后没再动过——连「▸ 开始」都没点过。

这不是用户不用心，是形状错了：**时段是汇报质量的前置条件，而记录动作要发生在干活的时候。**
没人会在一整天的干活中间记得点按钮；漏填没有任何提示，代价却是那段时间的活整段从汇报里
消失。**「不用就悄悄变差」是最糟的产品形状。**

### 更根本的错误：把「工作」等同于「agent 会话」

原设计假设「待办的工作都会产生 agent 会话，所以能用时间把它们对起来」。实际情况：
发邮件、开会、评审、跟人对齐方案这些工作**根本不产生会话**，它们在系统里唯一的痕迹
就是待办自己（标题、状态、子项、详情）。

而第一版实现里，`collect.mjs` 的 `groupByTodo` 有一句 `if (!list.length) continue;`——
**没有会话命中的待办进不了正文**。所以这类工作不管填不填时间，都不会出现在汇报里。
这条比时段方案本身更致命，也是用户提出「有些工作不依赖模型」时才被发现的。

### 现在的形状（§三–§六 的替代）

1. **归属交给模型**（`lib/report/attribute.mjs`）：把「待办清单（标题+项目+状态+子项进度，
   **不含 note**）」和按项目归并的会话素材一起给模型，让它输出「项目 | 待办序号 | 说明」。
   代价是归属不确定（每次跑可能略有不同），用户明确接受：零输入成本换确定性。
   解析容错，编造的项目名/越界序号一律丢弃（宁可漏配不可错配）；归属失败不令任务失败。

2. **证据分级**决定每条待办怎么进正文：

   | 证据 | 正文怎么写 |
   |---|---|
   | 有会话素材 | 模型写：做到哪了、产出什么 |
   | 无会话，但有子项/详情 | 材料是待办自身；**备忘标「需过滤」**交给模型改写（用户确认 note 是写给自己看的备忘，不是给上级的结论） |
   | 都没有 | 一行「状态：标题」，不编内容 |

3. **入场条件**：有会话素材 **或** 本窗内有变动（created/updated/completed 任一）。
   没动过的待办不进正文——报告讲的是这段时间干了什么，不是当前任务清单。
   （这条是 smoke 测试发现的：第一版把全部待办都塞进去，导致一期没动的待办也占一节。）

4. **时段、`due_at`、`/v1/todos/start|stop`、`/:id/spans` 全部删除**，包括 UI 上的时段表、
   「⏹ 结束」按钮、截止时间输入。待办回到「标题 + 状态 + 子项 + 详情」四件东西。

### 顺带修掉的两个同源 bug

展开箭头和「＋ 加子项」输入框**都**曾经是「有内容才显示」，而内容只能在展开区里添加——
干净的待办永远没有任何入口添加第一条子项或详情，这两个功能一直只有 agent 走 REST 才用得上。
现在两者都恒显示。

## 十、远程项目标签（同日晚追加）

### 需求

用户指出：待办里打了「黄区」标签的（黄区代码、黄区验证），**大概率不在这台机器上进行**。

### 为什么必须处理

用户当前就有一条「黄区kblas int8问题单处理」，而本机有真实的 kblas 会话。归属模型看到
「kblas」这个共同词，很可能把本机会话错配给这条待办——汇报里就会出现「在本机 kblas 上做了什么」
挂在一条根本不在本机做的问题单下面。这类错配比漏配更难发现，因为读起来完全合理。

### 做法

`providers.json` 的 `workbench.remoteProjects: ["黄区"]`（**标签由用户填，网关不内置
环境语义**——与「显示器只认 UUID/VCP、不内置方向/主机语义」同一条纪律）。

1. **不进归属候选**：`isRemoteTodo()` 过滤掉命中标签的待办，`userAttribute` 里另加一句
   提示告诉模型「这些标签不在本机做，清单里已排除；内容撞词是巧合，应归其他」。
2. **仍进正文**：标 `remote: true` → prompt 里写「［另一台机器上进行，本机无会话记录属正常］」，
   并禁止模型写成「没有进展」「缺少记录」这类判断。
3. **精确匹配**，不做子串：`黄区验证` 不会被 `黄区` 误伤（除非单独配置）。

配置入口在汇报页区间选择器下面一行（逗号/顿号/空格都是分隔符），走
`POST /admin/workbench/remote-projects`（回环 + JSON，与其它写端点同一威胁模型）。

## 十一、最终形态（同日第三次定向）：时段回归，但用途是日历事件

### 和 §九 撤销版本的区别（关键）

| | §九 撤销的版本 | 现在的版本 |
|---|---|---|
| `spans` 用来做什么 | 汇报的**会话归属**（时间重叠） | **产出日历事件**（每段一条 start~end） |
| 不填的后果 | 那段时间的活从汇报里**悄悄消失**（不可见） | 日历里**没有事件**（看得见的空白） |
| 失败模式 | 静默变差 | 显式缺失，且汇报不受影响 |

同一个字段、完全不同的失败模式。§九 撤销的理由是「不用就悄悄变差」，这里不成立——
日历同步本来就是「没记录就没有事件」，而且汇报的归属已经交给模型按内容判断，不再读 spans。

### 最终接口

```
todo.spans = [{ id, start, end }]      // end === null 表示进行中（未闭合）
```

- **记录方式两种都支持**：① 状态切换自动开闭（`PATCH status=in_progress` 开一段、
  `=done` 闭所有段，幂等）；② `PATCH /v1/todos/:id {spans:[...]}` 整组替换
  （id 留则保留——外部同步程序靠它认事件）。
- **显式传 spans 时不自动开闭**：调用方既然给了时间线，就不该被我们改写。
- **不限制全局单运行段**（§三 的旧约束已废除）：并行的两件事（开会 + 顺手改代码）
  是真实的，强约束会逼用户去手动改时间。
- 单段端点 + 动作端点：`POST /:id/spans`（加）、`PATCH·PUT /:id/spans/:sid`（改）、
  `DELETE /:id/spans/:sid`、`POST /:id/spans/open`、`POST /:id/spans/close`。
  open/close **不改 status**——「暂停」和「完成」是两件事。
- UI：收起行显示「进行中 42m」/「3 段 · 2h15m」；展开区是完整的时段表（起止可改、
  可删、可「＋ 补一段」手填）；有进行中时段的行多一个「⏸ 暂停」按钮。
- 未设时段的老待办**不带 spans 字段**（零迁移，不写空数组污染）。

### 日历同步约定（给外部同步程序）

每段 → Work 日历一条事件，`start`–`end`。进行中的段（`end === null`）按
「开始 → 现在」写入，闭段后再改写为准确结束时间。段 `id` 稳定（整组替换时传回即保留），
可以用它作为事件的幂等键。
